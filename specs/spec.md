# Spec — Dell-style Sales Prediction AI (Proof of Concept)

This file says **what** the proof of concept (PoC) must do and **why**. It does not choose
libraries or code structure; that is in `plan.md`. The step-by-step work is in `tasks.md`.

The scenario comes from `../dell.md`. Read that first if anything here is unclear.

---

## 1. Purpose

Build a small, working copy of the Dell sales prediction platform described in `dell.md`.

The goal is learning and demonstration, not production. When it is finished, the person should
be able to run the whole flow end to end and explain every part from real experience:

1. Sales data arrives in two ways: live through Kafka, and in scheduled batch files.
2. An ETL pipeline cleans and joins the data. ETL means Extract, Transform, Load.
3. Clean data is stored in three places: an S3 data lake, a vector store, and a Neo4j graph.
4. A forecasting step predicts future sales.
5. An AI layer answers questions in plain language using RAG and an agent.
6. A small web API (and optionally a simple dashboard) shows the results.

## 2. Constraints

These are fixed and the design must respect them.

- **No Docker.** Nothing may require Docker, Kubernetes or any local container.
- **Windows machine.** All local code must run on Windows with plain Python.
- **Managed cloud services only** for anything that needs a server:
  - Amazon S3 for the data lake.
  - Amazon S3 Vectors for the vector store.
  - Aiven for Apache Kafka for streaming.
  - Neo4j AuraDB Free for the graph database.
  - OpenRouter for the language model (LLM).
- **Low cost.** Data volumes stay small enough to fit free tiers where they exist
  (for example, AuraDB Free has node and relationship limits).
- **Made-up data only.** No real Dell or customer data. All data is generated by a script.
- **Secrets stay local.** Keys and certificates live in a `.env` file and a `secrets/` folder,
  and are never committed.

## 3. The business story (kept from dell.md)

A large company sells laptops, desktops, monitors, servers, storage and accessories. It sells
to consumers, small businesses and large enterprises, in four regions (North America, EMEA,
Asia-Pacific/Japan, Latin America), through three channels (online, retail partners, direct
sales).

Business users want to ask questions like:

- "What were laptop sales in EMEA last month, and how does that compare to the month before?"
- "Which enterprise customers who bought servers also bought storage?"
- "What do we expect monitor sales in North America to be over the next four weeks?"
- "Why did APJ desktop sales drop in March?"

## 4. Functional requirements

Each requirement has an ID such as FR-3. The ID is only a short name so tasks and tests can
point back to it.

### Data generation

- **FR-1 — Reference data.** Generate customers, products, regions and channels with stable IDs.
- **FR-2 — Historical sales.** Generate about 12 months of past transactions as batch files,
  one file per day, the way a daily export from a sales system would look.
- **FR-3 — Live orders.** Generate new orders one at a time and send them to Kafka as events.
- **FR-4 — Realistic problems.** On purpose, include messy data so the ETL has real work to do:
  duplicate transactions, missing values, wrong formats (dates and amounts as odd strings),
  unknown customer or product IDs, negative quantities, and events that arrive late.
- **FR-5 — Repeatable.** The same random seed always produces the same data.

### Ingestion

- **FR-6 — Batch ingestion.** A command uploads a batch file to the raw area of S3 and runs ETL
  on it.
- **FR-34 — Scheduled batch.** The batch command can also run on a schedule (every N minutes).
  Each time, it picks up only the daily files it has not loaded yet. This copies the "scheduled
  batch loads, for example once a day" in `dell.md`.
- **FR-7 — Stream ingestion.** A long-running consumer reads order events from Kafka and runs ETL
  on them in small groups (micro-batches).
- **FR-8 — Raw copy kept.** Every input, batch or stream, is saved unchanged in the raw area
  before it is cleaned, so any run can be replayed.

### ETL (transform)

- **FR-9 — One shared transform.** Batch and stream use exactly the same cleaning code, so the
  results are the same no matter how the data arrived.
- **FR-10 — Validation.** Check structure, data types, required fields and sensible ranges.
- **FR-11 — Cleaning.** Fix formats that can be fixed safely (dates, currency strings, text case).
- **FR-33 — Missing values filled or flagged.** As `dell.md` says, missing values are filled in
  or flagged, not just rejected. The rules are:
  - Missing `discount_pct` is filled with 0.
  - Missing `channel_id` is set to "Unknown", and the row is flagged.
  - Missing `unit_price` is filled with the product's list price, and the row is flagged.
  - Missing `transaction_id`, `customer_id`, `product_id`, `event_time` or `quantity` cannot be
    guessed safely, so the row goes to quarantine (FR-14).
  Flagged rows stay in the clean data with a `quality_flags` field that lists what was filled.
  The quality report counts them.
- **FR-12 — Duplicates removed.** Remove duplicates using `transaction_id`. If the same ID
  arrives twice, keep one record.
- **FR-13 — Joins.** Attach customer, product, region and channel details to each transaction.
- **FR-14 — Quarantine.** Rows that cannot be fixed are not dropped silently. They go to a
  quarantine area with the reason they were rejected.
- **FR-15 — Late events.** An event that arrives late lands in the correct date partition.

### Load

- **FR-16 — Data lake.** Clean transactions are stored in S3 as Parquet files, split by date.
- **FR-17 — Safe re-runs.** Loading the same data twice does not change the result. This is
  called an idempotent load.
- **FR-18 — Graph.** Customers, products, regions, channels and transactions, and the links
  between them, are loaded into Neo4j.
- **FR-19 — Vector store.** Short text summaries of the sales data (for example, "Laptop sales in
  EMEA, March 2026") are turned into embeddings and stored in S3 Vectors with metadata such as
  region, category and month. An embedding is a list of numbers that captures meaning.

### Data quality and monitoring

- **FR-20 — Quality report.** Every ETL run writes a short report: rows in, rows clean, rows
  clean but flagged, duplicates removed, rows quarantined and why.
- **FR-21 — Reconciliation.** Each run checks that rows in = rows clean + duplicates + quarantined.
  If not, the run fails loudly.
- **FR-22 — Logs.** All components write structured logs (one JSON object per line). This stands
  in for the Prometheus and ELK Stack monitoring in the real project.

### Forecasting

- **FR-23 — Weekly forecast.** Predict weekly sales amount per product category and region for
  the next 4 weeks.
- **FR-24 — Accuracy shown.** Report forecast error on held-back recent weeks, so we know how
  good the forecast is.
- **FR-25 — Forecasts stored.** Forecast results are saved to S3 so the AI layer can read them.

### AI layer

- **FR-26 — RAG answers.** For a question, find the most relevant summaries in S3 Vectors, give
  them to the LLM, and return an answer based on them. RAG means Retrieval-Augmented Generation.
- **FR-27 — Agent.** An agent can use tools to answer bigger questions: run a read-only SQL query
  on the data lake, run a read-only graph query on Neo4j, search the vector store, and read the
  forecast. It decides which tools to use and in what order.
- **FR-28 — Sources shown.** Every answer lists what it used (which tables, graph queries or
  summaries), so a person can check it.
- **FR-29 — Read-only safety.** The AI layer can never change or delete data.
- **FR-30 — Step limit.** The agent stops after a fixed number of tool calls, so it cannot loop
  forever or run up cost.

### Serving

- **FR-31 — Web API.** A FastAPI service offers: ask a question, get a forecast, get the latest
  quality report, and a health check.
- **FR-32 — Dashboard (optional).** A simple web page shows sales over time, the forecast, and a
  question box.

## 5. Out of scope

These are in `dell.md` but are left out of the PoC on purpose. Each could be a later step.

- Docker, Kubernetes and Terraform.
- Prometheus and the ELK Stack (replaced by JSON logs and quality reports, see FR-22).
- PySpark. The data is small, so pandas and DuckDB are enough.
- A React dashboard (a simple Python dashboard is used if FR-32 is built).
- Rewriting old Flask services (there are none in a new PoC).
- User login and permissions.

## 6. How we know it works (acceptance checks)

The PoC is done when all of these pass on a fresh run:

1. One command generates data, and the same seed gives the same files.
2. The batch pipeline loads 12 months of history into S3, and the quality report adds up (FR-21).
3. Running the batch pipeline a second time on the same files does not change the clean data.
   In scheduled mode, a new daily file dropped in is picked up on the next run, and files
   already loaded are skipped.
3a. A row with only a missing discount or channel is kept and flagged, not quarantined.
4. While the producer sends live orders, including duplicates and late events, the consumer
   loads them, and each transaction appears exactly once in the lake.
5. The same transaction loaded by batch and by stream appears exactly once.
6. Neo4j answers "which enterprise customers who bought servers also bought storage" correctly
   against a check done in SQL on the lake.
7. The forecast covers every category and region for 4 weeks and shows its error.
8. Each example question in section 3 gets a sensible answer with sources listed.
9. Unit tests for the transform logic pass without any cloud connection.

## 7. Open questions

- **Embedding model.** Check in the first cloud task whether OpenRouter offers an embeddings
  endpoint that suits us. If not, use Amazon Bedrock Titan Text Embeddings, since AWS is already
  in use.
- **Which LLM on OpenRouter.** Pick a model that supports tool calling and is cheap. The model
  name stays a setting, so it can be changed without code changes.
- **AWS region.** S3 Vectors is not offered in every AWS region. Confirm the region first.
